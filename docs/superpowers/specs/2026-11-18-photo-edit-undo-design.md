# 사진 편집 보강·되돌리기 설계

- 날짜: 2026-11-18
- 상태: 승인 (2026-11-18)
- 배경: P4·담당 채널 작업 뒤 실기기 재검증 피드백 (`docs/superpowers/specs/2026-11-18-web-channel-design.md` 후속)

## 왜

공유 화면과 수정 화면에서 사진을 다루는 일이 잦은데, 실수로 빼거나 지운 사진을 되살릴 방법이 없고, 수정 화면에서는 사진을 더할 수도 없다. 확인 모달은 바깥을 눌러도 닫히지 않아 답답하다. 저장·게시 전까지의 편집을 마음 편히 할 수 있게 한다.

## 목표

1. 공유 화면(`/share`)
   - [빼기] 버튼: 빨간색, 사진 안 오른쪽 위에 겹쳐 놓는다.
   - [빼기]를 누르면 확인 모달을 띄우고, 확인해야 뺀다.
   - 사진 목록 빈칸에 [+] 타일: 기기에서 사진을 골라 목록 끝에 더한다.
   - [되돌리기] [다시 하기] 버튼.
2. 수정 화면(`/posts/{id}/edit`)
   - 사진 [삭제]를 누르면 확인 모달을 띄운다.
   - [+]로 사진을 더한다. 새 사진은 [저장] 때 함께 올라간다(아래 "방식").
   - [되돌리기] [다시 하기] 버튼.
3. 메뉴의 [로그아웃]을 누르면 확인 모달을 띄운다.
4. 모든 확인 모달은 바깥(배경)을 누르면 닫힌다(취소와 같음). Esc로 닫히는 것도 그대로.
5. 개요 화면의 [확인]·[취소] 확인도 브라우저 기본 `window.confirm` 대신 같은 모달을 쓴다(4번을 모든 모달에 맞추기 위함 — 내 판단).

## 하지 않는 것

- 저장·게시한 뒤의 되돌리기. 기록은 화면을 떠나면 사라진다.
- 메모·캡션 등 글자 입력의 되돌리기. 키보드·브라우저 기본 되돌리기를 쓴다(내 판단: 글자마다 기록이 쌓이면 버튼이 오히려 불편).
- 사진을 더했을 때 Claude 재분석이나 캡션 재생성. 캡션은 그대로다.
- 새 사진의 초점(분석이 찾은 술병 위치) 계산. 새 사진은 초점 없이 기본 자르기(가운데)로 렌더한다. 여백 넣기로 바꿀 수 있다.

## 하면 안 되는 것 (실패로 본다)

- 되돌리기·추가 중 사진이 10장을 넘어 저장·전송되는 것.
- [저장]이 실패했는데 일부 사진만 올라가 게시물이 어중간한 상태로 남는 것.
- 되돌리기로 이미 저장된 사진이 서버에서 지워지는 것 — 서버는 [저장] 시점의 최종 목록만 안다.
- 쓰이지 않는 업로드 파일이 서버에 남는 것.

## 방식 (사용자 선택: A)

**A. [저장]할 때 새 사진을 함께 올린다.** [+]로 고른 사진은 브라우저 안에서 미리보기로만 보이고, 되돌리기·다시 하기도 브라우저 안에서만 일어난다. [저장] 요청 하나에 기존 사진 id와 새 파일을 최종 순서대로 담는다.

검토했던 다른 방법:
- B. [+]를 누르는 즉시 서버에 올리고 id를 받는다. 저장이 빠르지만, 올렸다 되돌리거나 저장하지 않고 나간 사진을 지우는 정리 작업이 필요하다. 저장 전까지만 되돌린다는 요구와 맞지 않아 뺐다.

## API

`PUT /api/v1/posts/{id}`를 multipart로 바꾼다.
- 파트 `request`: 지금의 `PostUpdateRequest` JSON. `photos` 항목은 기존 사진이면 `{id, fitMode}`, 새 사진이면 `{newIndex, fitMode}`(새 파일 파트의 순번). 둘 중 정확히 하나.
- 파트 `newPhotos`: 새 사진 파일들(0개 이상).
- 최종 사진 수는 1~10장(`PostIntakeService.MIN_PHOTOS`·`MAX_PHOTOS`와 같은 규칙). 어기면 기존 검증 에러 코드(`api-conventions`)로 400. 새 에러 코드는 만들지 않는다.
- 새 파일은 공유 접수와 같은 경로로 처리한다: 형식 검사·디코딩·원본 저장·CROP 렌더(초점 없음). 접수 쪽 단계(stage → promote)를 재사용해 DB 커밋 전에는 임시 위치에만 있고, 실패하면 임시 파일을 지운다. 커밋 뒤 버려진(빠진) 사진 파일 삭제는 지금처럼.
- 원본 파일 경로는 기존 사진과 겹치지 않아야 한다(지금은 `originalPath(postId, position, format)`라 위치가 겹칠 수 있음 — 저장 시 고유한 이름을 쓰도록 바꾼다).
- 버전 검사·담당 채널 전환(`moveToWeb`)·편집 이벤트는 지금과 같다.
- 웹이 JSON으로 보내던 기존 호출은 남기지 않는다(웹이 유일한 클라이언트).

## 웹

### 되돌리기·다시 하기
- 공유 화면과 수정 화면 각각, 화면 상태 중 **사진 목록(순서·추가·빼기·여백)과 별점**만 기록한다.
- 한 번의 조작(빼기 확인, 추가 한 번, 위로/아래로, 여백 전환, 별점 바꾸기)이 기록 한 칸.
- 새 조작을 하면 다시 하기 기록은 지운다. 기록 한도 50칸(내 판단).
- 버튼은 사진 목록 위에 [되돌리기] [다시 하기]로 둔다. 할 게 없으면 비활성. 사진 애니메이션 중에도 비활성.
- 되돌리기로 빠진 사진이 돌아오면 원래 자리로 돌아온다.
- 공용 훅(예: `useUndoable(initial)` → `{state, set, undo, redo, canUndo, canRedo}`)으로 두 화면이 같이 쓴다.

### 사진 추가 [+]
- 사진 목록 끝 빈칸에 [+] 타일. 누르면 파일 선택(`accept="image/*"`, 여러 장).
- 10장을 넘게 고르면 넘는 만큼은 더하지 않고 안내 문구를 보인다(공유 화면의 11장 이상 처리와 같은 말투). 10장이면 [+]를 숨긴다.
- 수정 화면의 새 사진은 미리보기(브라우저 객체 URL)로 보이고, 여백 넣기·순서 바꾸기는 기존 사진과 똑같이 된다.

### [빼기] 버튼 (공유 화면)
- 빨간 동그란 버튼, 사진 안 오른쪽 위. 손가락으로 누르기 충분한 크기(44px 이상). 접근성 이름은 "사진 N 빼기".

### 확인 모달
- 공유 화면의 `ConfirmDialog`를 `components/ui/ConfirmDialog.tsx`로 옮겨 모든 화면이 같이 쓴다.
- 바깥(배경) 클릭 = 취소. 문구:
  - 사진 빼기/삭제: "이 사진을 뺄까요?" / [빼기] [취소]
  - 로그아웃: "로그아웃할까요?" / [로그아웃] [취소]
  - 개요 [확인]·[취소]: 지금 문구 그대로("인스타그램에 게시할까요?", "이 게시물을 취소할까요?").

## 정해 둔 세부 (내 판단)

- 캡션·해시태그·텔레그램: 사진 수·순서는 캡션에 들어가지 않으므로 캡션 재생성 판단(`decideCaption`)은 지금 그대로다. 수정 화면 저장은 담당을 WEB으로 넘기므로 텔레그램 미리보기를 다시 만들 일도 없다. 개요 화면은 다시 읽은 상세로 새 사진을 보여 준다.
- 수정 가능한 상태: 지금 수정 저장이 허용하는 상태·버전 검사를 그대로 따른다. 분석 중·게시 중에는 지금처럼 저장 자체가 막힌다.
- 처리 순서: 새 파일 검사·디코딩·렌더·임시 저장(stage)을 트랜잭션 밖에서 먼저 끝내고 → 쓰기 트랜잭션(버전 검사·사진 행 추가/삭제/순서) → 커밋 뒤 정식 위치로 옮김(promote)·빠진 파일 삭제. 어느 단계든 실패하면 임시 파일을 지우고 DB는 바뀌지 않는다. 공유 접수(`PostIntakeService.receiveInputs`)와 같은 모양이다. 렌더는 요청 안에서 동기로 끝낸다.
- 저장 실패(409 충돌 등): 웹은 새 사진 파일을 포함한 편집 상태와 되돌리기 기록을 그대로 둔다. 사용자가 다시 [저장]하면 같은 파일을 다시 보낸다.
- 에러 코드: 새 파일의 형식·디코딩·용량 오류는 공유 접수가 쓰는 기존 코드를 그대로 쓴다. 업로드 크기 제한(`application.yml` 파일당 20MB, 요청 210MB)도 그대로.

## 빌더에게 맡기는 것

- 되돌리기 상태 저장 구조, 새 사진의 임시 키 방식.
- multipart 파트를 Spring에서 받는 방식(`@RequestPart`).
- 버튼 아이콘 모양·색 세부(빨강은 기존 Tailwind 팔레트의 red 계열).
