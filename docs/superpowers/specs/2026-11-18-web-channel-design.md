# 담당 채널 분리와 웹 개요 화면 설계

- 날짜: 2026-11-18
- 상태: 승인됨
- 선행: `2026-11-14-review-to-instagram-design.md` (이하 "기존 설계"), P4 계획 `plans/2026-11-18-review-to-instagram-p4-web-ops.md`
- 계기: P4 배포 뒤 실제 기기 검증(2026-11-18) 피드백

## 의도

웹(PWA)에서 시작한 일은 웹에서 끝나고, 텔레그램에서 시작한 일은 텔레그램에서 끝나게 한다. 지금은 어느 경로로 들어온 게시물이든 접수·개요·[확인]·게시 결과가 모두 텔레그램으로 가서, 갤러리 공유로 웹에서 보낸 사람이 텔레그램으로 넘어가야 한다. 웹에서 보냈으면 그 화면에서 개요를 보고 바로 [확인]하는 것이 자연스럽다.

기존 설계의 "게시 전 확인" 결정(웹 미리보기 ✗, 텔레그램 개요 ✓)을 이 문서가 바꾼다. "모든 게시는 사람이 확인한 뒤에만" 이라는 안티 목표는 그대로다. 확인하는 장소만 담당 채널을 따른다.

같은 검증에서 나온 화면 결함·개선(검색 엔터, 콤보박스, 사진 버튼, 11장 처리, 로그아웃)도 이 작업에 넣는다.

## 목표

1. 게시물마다 **담당 채널**(`TELEGRAM` / `WEB`)을 둔다. 알림·확인·취소·재시도·게시 결과는 담당 채널에서만 일어난다.
2. 웹 담당 게시물을 위한 **개요 화면**(`/posts/{id}`): 분석 진행 → 개요 → [확인]·[수정]·[취소] → 게시 진행 → 완료/실패.
3. 공유 화면 [보내기]에 **확인 모달**을 두고, 보낸 뒤 개요 화면으로 간다.
4. 수정 화면·공유 화면 결함 수정과 로그아웃 추가.

## 비목표

- 웹 푸시 알림(Web Push). 웹을 닫으면 분석 완료를 알 수 없지만, 다시 열면 기록 목록·개요 화면에서 상태를 본다.
- 실시간 연결(SSE·WebSocket). 폴링으로 충분하다(아래 접근 방식).
- 웹 담당 게시물을 다시 텔레그램 담당으로 돌리는 기능.
- 텔레그램 [상세] 버튼 변경. 지금처럼 텔레그램 메시지로 사진과 전체 캡션을 보낸다.

## 안티 목표

- 웹 담당 게시물인데 텔레그램에 알림이나 살아 있는 버튼이 남는 것.
- 담당이 아닌 채널에서 [확인]이 먹혀 두 번 게시되거나 확인 없이 게시되는 것.
- 웹 개요 화면이 실제 게시될 내용(사진 순서·여백·캡션)과 다른 것을 보여 주는 것.

## 담당 채널 규칙 (사용자 결정)

| 상황 | 담당 |
|---|---|
| 텔레그램 봇으로 사진을 보냄 | `TELEGRAM` |
| 갤러리 공유 → 웹 [보내기] | `WEB` |
| 텔레그램 [수정] 링크로 웹 수정 화면을 열고 **[저장]** | 저장 순간부터 `WEB` (사용자 결정 (가)) |
| 같은 링크를 열기만 하고 저장하지 않음 | `TELEGRAM` 그대로. 텔레그램 개요의 [확인]이 살아 있다 |
| 텔레그램 [확인]·[취소] | 텔레그램에서 처리, 결과도 텔레그램 |
| 텔레그램 [상세] | 텔레그램 메시지로 사진·전체 캡션 (사용자 결정 (ㄱ), 담당 안 바뀜) |

- `WEB`으로 바뀌는 방향만 있다. 한 번 `WEB`이면 계속 `WEB`이다.
- 웹 수정 화면에서 [저장]하면 담당과 상관없이 결과는 `WEB`이다(이미 `WEB`이면 그대로).

## 접근 방식

### 담당을 어떻게 알까

| 방식 | 장단점 | 선택 |
|---|---|---|
| **A. `post.channel` 컬럼 추가** | 규칙이 데이터 한 칸으로 드러난다. 알림·콜백·웹 API가 같은 값을 본다. 마이그레이션 1개. | ✓ |
| B. 기존 `source` + "웹에서 저장한 적 있음" 플래그로 계산 | 컬럼 의미가 둘로 나뉘고 판정 코드가 여러 곳에 퍼진다. | ✗ |

`source`는 "어디서 들어왔나"로 그대로 둔다(기록·통계용). `channel`은 "지금 누가 처리하나"다.

### 웹 화면 갱신

| 방식 | 장단점 | 선택 |
|---|---|---|
| **A. React Query 폴링** (진행 중 상태일 때만 3초 간격) | 기존 `GET /api/v1/posts/{id}`를 그대로 쓴다. 사용자 1명이라 부하 문제 없음. | ✓ (Claude 판단) |
| B. SSE | 몇 초 빠르지만 Next rewrites 프록시·역방향 프록시 타임아웃·재연결 처리가 붙는다. | ✗ |

## 동작

### API

1. **마이그레이션 `V10__post_channel.sql`**: `post.channel VARCHAR(16) NOT NULL`. 기존 행은 모두 `TELEGRAM`(이미 텔레그램으로 알림이 나간 게시물이다).
2. **`PostChannel` enum** `TELEGRAM, WEB`. `Post.receive`가 `source`로 초기값을 정한다: `TELEGRAM`→`TELEGRAM`, `SHARE`→`WEB`. `Post`에 `moveToWeb()`.
3. **수정 저장(`PostEditService`)**: 쓰기 트랜잭션 안에서 `moveToWeb()`. 이전 담당이 `TELEGRAM`이었고 `telegramMessageId`가 있으면, 커밋 뒤 그 개요 메시지의 버튼을 지운다(`TelegramClient.removeKeyboard`). 새 개요는 텔레그램에 보내지 않는다.
4. **알림 차단**: `PostNotifier`의 모든 `notify*`는 게시물 담당이 `WEB`이면 아무것도 보내지 않는다(한 곳에서 판정). `NotificationReconciler`도 `WEB`은 건너뛴다. 담당 판정은 알림 시점의 DB 값으로 한다(저장 직후 이벤트가 이미 `WEB`을 본다).
5. **텔레그램 콜백**: `CallbackHandler.dispatch`에서 담당이 `WEB`이면 `stale()`. 버튼은 3에서 지워지지만, 지우기 실패·경합에 대한 마지막 방어다.
6. **웹용 동작 API** (`PostController`, `api-conventions` 스킬 형식 그대로):

   | 메서드·경로 | 본문 | 하는 일 |
   |---|---|---|
   | `POST /api/v1/posts/{id}/confirm` | `{ "version": n }` | `PublishService.confirm` |
   | `POST /api/v1/posts/{id}/cancel` | `{ "version": n }` | `PENDING_REVIEW`→`CANCELED` 조건부 전이 (콜백의 cancel과 같은 쿼리) |
   | `POST /api/v1/posts/{id}/retry` | `{ "version": n }` | 실패 단계가 분석이면 재분석, 게시면 `PublishService.retry` (콜백 retry와 같은 분기) |

   - 담당이 `TELEGRAM`인 게시물이면 409 `POST_NOT_EDITABLE`.
   - 상태가 맞지 않거나 `version`이 다르면(`ConfirmResult.STALE` 포함) 409 `POST_VERSION_CONFLICT`.
   - `CAPTION_TOO_LONG`이면 400 `POST_CAPTION_TOO_LONG`.
   - 성공은 갱신된 `PostDetailResponse`(200). 새 에러 코드는 만들지 않는다.
   - 콜백과 웹 API가 같은 로직을 쓰도록 cancel·retry 분기는 서비스로 옮긴다(콜백은 그 서비스를 부르고 알림만 덧붙인다).
7. **`PostDetailResponse`·`PostSummaryResponse`에 `channel`** 추가.

### 웹

#### 공유 화면 (`/share`)

- [보내기] → **확인 모달**: 사진 수, 별점(없으면 "없음"), 메모 앞부분을 보여 주고 [보내기]·[돌아가기]. 모달의 [보내기]가 실제 전송이다.
- 전송 성공 → `/posts/{id}`로 이동(`router.replace`, 뒤로 가기로 공유 화면에 돌아가 다시 보내지 않게).
- **11장 이상**:
  - 별점·메모 입력을 비활성.
  - [보내기] 버튼 글자를 안내 문구로 바꾼다: `사진을 10장 이하로 줄여 주세요 (지금 N장)`. 버튼은 비활성. 기존 버튼 아래 빨간 문구는 없앤다.
  - 사진마다 [빼기] 버튼. 10장 이하가 되면 모든 입력과 [보내기]가 정상으로 돌아온다.
  - 뺀 사진은 이번 전송에서만 빠진다(공유 캐시 원본은 전송 성공 시 기존처럼 정리).
- 10장 이하일 때도 [빼기]는 보인다(1장 남으면 [빼기] 비활성).

#### 개요 화면 (`/posts/{id}`, 신규)

상태별로 보여 준다. 진행 중 상태(`RECEIVED`·`ANALYZING`·`PUBLISHING`)에서만 3초 폴링.

| 상태 | 보이는 것 | 버튼 |
|---|---|---|
| `RECEIVED`·`ANALYZING` | "분석 중입니다" + 진행 표시 | 없음 |
| `PENDING_REVIEW` | 게시될 사진(렌더 결과, 순서대로), 술 이름·양조장(주소·전화·홈페이지·계정), 별점, 전체 캡션 | [확인] [수정] [취소] |
| `PUBLISHING` | "게시 중입니다" | 없음 |
| `PUBLISHED` | 완료 문구 + 인스타그램 링크(`permalink`) | 없음 |
| `FAILED` | 실패 단계와 `failureReason` | [다시 시도], 수정 가능하면 [수정] |
| `CANCELED` | "취소한 게시물입니다" | 없음 |

- [확인]·[취소]는 각각 확인 대화상자 한 번(게시는 되돌릴 수 없음). 누르는 동안 모든 버튼 비활성.
- 409를 받으면 문구를 보이고 게시물을 다시 불러온다.
- **담당이 `TELEGRAM`인 게시물**: 상태와 내용은 보여 주되 [확인]·[취소]·[다시 시도] 대신 "텔레그램에서 진행 중인 게시물입니다." 문구. 수정 가능하면 [수정]만 보인다.

#### 수정 화면 (`/posts/{id}/edit`)

- [저장] 성공 → `/posts/{id}`로 이동. "텔레그램으로 새 개요를 보내 드립니다" 문구는 없앤다.
- **검색 입력 엔터**: 폼 전체 제출을 막는다. 검색 결과가 있으면 첫 항목을 고른다.
- **술·양조장 검색 콤보박스**: 항목을 고르면 검색어를 비우고 결과 목록을 닫는다. 고른 항목은 위 "선택한 술/양조장" 줄에 표시되고, 목록에 다시 보일 때는 선택 표시(체크·강조)를 한다. 키보드 위/아래로 항목 이동은 Claude 판단으로 넣는다(접근성 기본).
- **사진 버튼**: 위로·아래로·삭제·여백 넣기 버튼을 사진 위에 겹쳐 놓는다(작은 아이콘 버튼, 반투명 배경). 누르면 순서 바뀜·삭제·여백 변화가 애니메이션(200ms 안팎)으로 보이고, 애니메이션 동안 모든 사진 버튼 비활성. `prefers-reduced-motion`이면 애니메이션 없이 즉시.

#### 기록 목록 (`/`)

- 각 행은 `/posts/{id}`(개요 화면)로 간다. 지금처럼 수정 화면으로 바로 가지 않는다.

#### 로그아웃

- 주 메뉴(`AppNav`)에 [로그아웃]. 누르면 기존 세션 삭제 API를 부르고 `/login`으로 이동, React Query 캐시를 비운다.
- 사용자가 말한 "부수 기능"은 이번 범위에서 로그아웃만 넣는다. 다른 것은 목록이 정해지면 따로 한다.

### 문서

- `docs/telegram-messages.md`: 웹 담당 게시물은 메시지를 받지 않는다는 규칙, 저장 시 이전 개요 버튼 제거.
- 기존 설계 문서 "게시 전 확인" 표에 이 문서로 바뀌었다는 변경 줄 추가.
- P4 계획 "검증 결과 (Task 9) Step 2"에 이번 검증 결과 기록(1번 미확인, 2·5는 이 설계로 이어짐, 3 로그아웃 없음→추가, 4·6·7·8 통과).

## 제약

- 기존 설계의 제약 전부(스택, 도메인 로직은 `apps/api`에만, 응답 포맷 `api-conventions`).
- 상태 전이 표(`PostStatus`)는 바꾸지 않는다.
- 같은 게시물이 두 번 게시되지 않는다: 웹 API도 `version` 조건부 전이를 거친다.
- 텔레그램·캡션 문구가 바뀌면 `docs/telegram-messages.md`·`docs/instagram-caption.md`도 고친다.

## 빌더에게 맡기는 것

- 폴링 간격 3초를 조정할 근거가 있으면 조정.
- 서비스 메서드 이름·패키지 위치.
